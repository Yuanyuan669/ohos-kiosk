整体优化方向（基于 LHT16 / API 11，编译目标 API 10）

结论先说：此前没有一篇"整体优化方向"的文档。优化相关的结论散在 DEVLOG（每次改动）、
PITFALLS（踩坑与修法）、TOOLCHAIN-NOTES（工具链选型）和 README（使用与故障码）里。
这篇把"往哪优化、先做什么、怎么验收"固定下来，后续按它排优先级；单次改动仍记 DEVLOG。

一、边界和前提（别越过这些去做优化）
  - 不刷机、不改只读系统分区。应用侧优化为主；系统侧只做配置和厂商允许的事。
  - 编译目标保持 API 10，设备实际 API 11（OpenHarmony 4.1.7.5）。升 API 11/12 是待评估项，
    不是默认动作。
  - 主机是 Windows + Git Bash，工具链在 D 盘（SDK 4.0-Release / hvigor 3.2.4 / JDK 17）；
    CI 用 self-hosted runner（模板见 ci/），Linux runner 优先。
  - 应用零三方依赖（不拉 ohpm 外网包），ArkTS Stage 模型。
  - 设备出网环境不稳定：open-meteo 被 reset、GitHub raw 直连失败、*.workers.dev 不可达。
    所有远程数据优化都要以"网络随时会断"为前提。

三、优化方向（按优先级）

P0 长稳与无人值守（信息屏的核心体验，目前缺口最大）
  1. 开机自启 / 断电恢复：现状没有。当前只有 launcher 入口，断电后需要人点图标。
     普通三方应用默认拿不到开机广播；可选路径：
       a) 外部 watchdog（推荐先做）：局域网里一台常开机器定时 `pidof || aa start`，
          通过 TCP 模式（OHOS_TARGET）执行，不改设备系统；
       b) 向厂商要系统签名/预装，做成 system app 后申请开机自启；
       c) 换成 kiosk launcher 方案（侵入性最大，暂不考虑）。
     验收：断电重启 3 次，5 分钟内自动回到信息屏。
  2. 崩溃自愈：现状没有。与 1 共用外部 watchdog；应用侧在 EntryAbility 记录
     onDestroy/onForeground 时间，便于判断是否异常退出。
     验收：`kill -9` 后 2 分钟内恢复。
  3. 长时间挂前台的自检：目前 onPageShow 会重载设置/照片，但没有周期性自检。
     建议每小时记录一次 RSS/网络状态到 hilog，watchdog 侧抓取；发现内存持续上涨就重启应用。
  4. 日志与故障留存：现在只有 hilog 和 faultlog。watchdog 每日抓一次
     `hilog -x -T HomeKiosk` 与 faultlog 清单，保留 7 天，避免问题发生后无据可查。

P0 网络韧性（外部风险最大，直接影响卡片是否空白）
  5. "最后一次成功值"缓存：现在天气失败会变"离线"，feed 失败会变"不可达"，AQI 直接变 --。
     应把每个数据源最后成功的结果 + 时间戳持久化（preferences 或 rawfile），断网时显示
     stale 值并标注更新时间，而不是清空。股市已有 rawfile 内置快照，天气/feed/AQI 还没有。
     验收：拔网 30 分钟，所有卡片仍有内容且能看到"数据时间"。
  6. AQI 兜底：AQI 与天气同属 open-meteo 域，当前网络下主源被墙时 AQI 永远 `--`。
     要么增加备用源，要么在失败时隐藏 AQI 而不是显示占位。
  7. feed 多地址：设置页目前只允许一个 URL。可改成多行候选，按顺序尝试，
     与股市镜像列表同一套策略。
  8. 股市汇总请求串行 6 s × 6 个镜像，最坏 30 s+ 才返回。建议并发竞速
     （先成功者胜出）或把单源超时降到 3 s；同时避免每 5 分钟重复打全部镜像。
  9. 网络变化监听：接入 `@ohos.net.connection`，网络恢复时立即刷新一次，
     而不是等下一个 120 s 重试窗口；省电也更快恢复。
  10. 图片/JSON 体积：kiosk_summary.json 目前 7.5 KB，可接受；如果 TradingMaster 输出变大，
      考虑裁剪字段或 gzip（需自行解压）。

P1 功耗、发热与屏幕
  11. 夜间调光：当前常亮 + 全屏，没有时间段调光。应用侧可叠加半透明黑层按时间切换；
      调系统亮度需要权限/系统接口，先在实机验证可用性。验收：夜间不刺眼、白天可读。
  12. 照片在后台空转：MediaCard 只要有股市数据就显示股市，但心跳里仍每 15 s 解码一张照片
      （heartbeat 只判断 photoCount，没有判断当前是否在显示照片）。这是明确的 CPU/内存浪费。
      要么把照片并入股市面板作为其中一页，要么在股市面板可见时暂停解码。
  13. 定时器对齐：时钟 1 s 是必须的；天气/feed/股市的定时器可对齐到整分钟，
      合并在同一个 tick 里判断，减少碎片唤醒。
  14. 照片轮播间隔 15 s 偏短，对信息屏可放宽到 60 s；LCD 无烧屏风险，主要收益是省 CPU。

P1 渲染与内存
  15. RSS 187 MB 偏高，先拆解再优化：空页面、加载 1 张照片、加载股市 JSON 三种状态各测一次，
      确认是 PixelMap、ArkUI 缓存还是 rawfile 解析占用。没有测量前不要盲调。
  16. 照片解码尺寸按屏幕高度算（1080），而不是固定长边 1280；同时确认 ImageSource 释放干净
      （PixelMap 已 release，ImageSource 也应有 release 路径）。
  17. 自选股列表用 ForEach 全量渲染，条目多时首帧会慢；可换 LazyForEach 或限制首屏条数。
  18. 时钟每秒更新会让使用 clockText 的组件重组；可把时钟拆成独立组件，
      把秒级刷新限制在局部，减少整页 diff（先用帧率/CPU 数据验证是否值得）。

P1 构建与 CI
  19. 冷 CI 每次要下 2 GB SDK 和 hvigor：给 self-hosted runner 加目录缓存（或持久化 $OHOS_TOOLS），
      key 用 SDK/hvigor 版本 + 校验和。目标：冷 CI < 15 分钟，热 CI < 3 分钟。
  20. 版本固定与校验：SDK 4.0.10.13、hvigor 3.2.4、JDK 17；CI 下载后校验 SHA256，
      不追最新。升级当作独立变更，先在本机跑通再改 CI。
  21. release 构建对比：当前默认 debug。用 buildMode=release 出一次包，比较体积和启动时间，
      再决定是否把 CI 产物切到 release（签名流程不变）。
  22. 视觉回归：CI 定时跑 deploy + 截图，和基准图做尺寸/哈希对比；布局类回归能自动发现。
  23. 设备不可达时 CI 只产出构建+签名 artifact，不把流水线判红（模板已按 warning 处理 doctor，
      继续沿用）。

P2 工具链与系统（收益不确定，按需）
  24. API 10 → 11（2026-11-16 已评估）：SDK 4.1-Release 已就绪（$OHOS_TOOLS/sdk，输入法工程在用），
      hvigor 3.2.4 兼容 API 11 编译实测通过。但 kiosk 直接升 target 会触发 9568282
      "releaseType target not same"，无法覆盖安装（卸载重装丢照片/配置）。
      结论：保持 API 10；升级前置条件是先写"数据迁移脚本"（pull/push 照片与 preferences，
      卸载→装 API 11 包→回灌），迁移脚本本身作为独立变更。
  25. API 12 / 5.0 刷机：只有出现必须的新能力才做；刷机有变砖风险，先按 DEVICE.md 备份。
  26. hdc 双版本自动选择：现在两个 hdc 都能用，脚本靠 HDC 覆盖；可加"列举失败自动换另一个"，
      减少换机器时的手动步骤。
  27. Linux runner 优先：Windows 上的 Git Bash 路径转换坑已修，但 Linux 更省心；
      Windows 只保留为开发机。

P2 安全与分发
  28. 当前签名证书来自 SDK 公开测试 CA，只适合家用自装；对外分发要向厂商申请正式证书。
  29. Profile 有效期到 2033；bundleName 改动必须重签；密钥离线备份，不进仓库（已做）。
  30. 权限保持最小（目前仅 INTERNET）；后续加定位/存储/后台能力时逐项评估。
  31. feed/kiosk_summary.json 只放公开市场汇总，不含账户、持仓、token（DEVLOG 已约定），
      后续自动化也要守住这条。

四、不建议做的事（反目标）
  - 为了省内存去 root 改系统、停系统服务：收益小、风险大、不可持续。
  - 为了追新刷 5.0/API 12：当前应用没有必须依赖的新 API，刷机风险大于收益。
  - 引入三方 UI/网络框架：包体、兼容性和无外网 ohpm 都会反噬，现有零依赖是优势。
  - 盲目把刷新间隔调到秒级：数据源本身是分钟级，只会增加失败率和耗电。
  - 用 WebView 套网页替代 ArkUI：启动慢、常驻内存高、离线不可控。
  - 没有测量就优化：先记录基线，再改，再对比。

六、建议的行动顺序
  1) 外部 watchdog + 每日健康检查（不改系统，直接解决自启/自愈/观测三件事）
     —— 2026-11-16 已落地：scripts/watchdog.sh（--once / --loop 60），设备侧零改动。
     覆盖：进程拉起（kill -9 实测 ~3 s 恢复）、每小时 RSS 采样（watchdog-logs/<日期>/rss.log，
     首采 193612 kB ≈ 189 MB，与基线一致）、每日 09:30 跳落 hilog + faultlog 留存 7 天。
     调度建议：schtasks 每 10 分钟 --once（示例见脚本头注释）；TCP 模式带 OHOS_TARGET。
  2) 远程数据 stale 缓存 + AQI 兜底 + 股市请求并发化
  3) 测量 RSS 构成，按屏幕高度解码照片，股市面板可见时暂停照片解码
  4) 夜间调光 + 定时器对齐 + 照片轮播放宽
  5) CI 缓存、release 构建、视觉回归
  6) 评估 API 11（可选），API 12 仅在必要时

七、记录约定
  - 每次优化改动在 docs/DEVLOG.md 记"改前数据 / 改法 / 改后数据"。
  - 跨阶段的方向调整更新本文；踩坑仍记 docs/PITFALLS.md。
  - 没测量的优化不做结论；目标值可以改，但改的时候要写原因。
